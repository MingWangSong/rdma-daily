读一个 4 KiB 缓存块，谁在搬数据？

学完能做到：沿两台机器画出一次读的路线，解释单边 RDMA READ 省了谁的工作，又有哪些工作必须留在存储软件里。

先备知识原文路线跟读数据路径读实验图练习与答案资料

01 / 先把问题缩小（4 分钟）

计算节点 A 想读存储节点 B 上的一个 4 KiB 文件块。B 用主存做缓存：命中就取现有字节，未命中则由存储软件决定读本地 SSD、访问下层存储，还是返回未命中。今天不讨论副本协议，只比较同一个已命中缓存的块怎样抵达 A。

  • 主存（DRAM）是程序和设备工作时存放字节的地方，掉电通常不保留；不等于 SSD，也不等于图 1 的 CPU 三级缓存（L3）。后者是机器内部的硬件缓存，前者上的“文件缓存”是存储系统管理的内容。
  • RNIC 是支持 RDMA 的网卡；PCIe 是设备与主机之间的本地通路；DMA 是设备直接读写主机内存，不需 CPU 逐字节搬运。RDMA 把这种设备参与的数据搬运延伸到两台机器之间。
  • RPC（远程过程调用）是请远端应用做一件事，例如 get(block_id)。它描述的是请求语义，可以跑在 TCP 上，也可以用 RDMA 的操作实现。RDMA READ 描述的是网卡执行的具体搬运：从指定远端内存地址取字节。

02 / 原文路线：先找硬件，再找动词（5 分钟）

  1. PDF 第 3 页：§2 开头、图 1。从外侧两条 InfiniBand 链路向内找 Connect-IB 网卡、PCIe 3.0 ×16、PCIe 控制器、L3 和 DRAM。圈出网卡跨过的接口：左边是机器间网络，右边是机器内 PCIe。这是一台 2016 年实验机器的拓扑，不是每台服务器都相同的接线图，也不是一个请求的时序图。
  2. PDF 第 3–4 页：§2.2.1 和表 1。读到 memory verbs 与 messaging verbs 时暂停：SEND 的接收地址是谁指定的？READ 的远端地址是谁指定的？ §2.2.2 只需知道工作队列条目是硬件可读的任务描述，头部字节和后续优化暂时跳过。

读图时别把 CPU 封装和 CPU 核心当成一回事。经过图 1 中的 PCIe 控制器、L3 并不意味着远端应用线程执行了查找或复制。图中也没有 SSD，因此不能用它证明“网卡能独立查文件”。

03 / 跟一遍 4 KiB 的数据路径（7 分钟）

RPC：我知道块号，不知道地址

  1. A 的应用发 get(block_id)。
  2. B 的存储应用解读块号，从索引查到内存位置，检查访问权限与版本。若没命中，由同一层决定走慢路径。
  3. B 的应用组织响应，网卡传输；A 收到应用响应后得到数据或明确错误。若底层用 RDMA SEND/RECV，接收方软件事先放好接收缓冲区，接收网卡按那个缓冲地址写入，再由接收方软件消费消息。

单边 READ：我已拿到地址和许可

  1. 前提：B 的软件已注册允许访问的缓冲区，A 知道远端地址、授权访问的远端键（rkey）、长度，并准备好本地接收位置。地址如何从块号得到，是额外的设计问题。
  2. A 的 CPU 提交 READ；A 的 RNIC 发请求。B 的 RNIC 验证权限，从注册的主存缓冲区经主机接口取字节，返回给 A，不必每次唤醒 B 的应用线程。
  3. A 的 RNIC 把返回字节放到本地内存。对于请求了完成通知的 READ，A 的软件看到成功完成后才能按约定使用缓冲区；仍要按存储协议验证版本等业务条件。

论文表 1 的三种传输中，只有 RC（Reliable Connected，可靠连接）支持 READ；RC、UC、UD 都支持 SEND/RECV，但 UC 可 WRITE 不可 READ，UD 不提供这两种内存操作。这是该表比较的范围，不是所有后来传输的总表。“单边”指远端无需提交与这条 READ 对应的接收工作；不是只有一台网卡工作，也不是全程没有 CPU。

可选：QP、WQE 和 CQE 分别是什么？

QP（Queue Pair）是一对发送与接收工作队列；WQE（Work Queue Element）是一条网卡要执行的工作描述；CQ（Completion Queue）是软件查看结果的完成队列，CQE是其中一条完成记录。提交只是排队，不代表已经执行。成功 READ 的完成表示此操作的数据已到本地，不表示数据是最新版本；成功 WRITE 的完成也不能替代存储系统对副本或 SSD 落盘的确认。

04 / 读一张实验图：为什么速度曲线会换瓶颈？（5 分钟）

打开 图 12(a)(b)，PDF 第 10 页，再看 §5.3.1，PDF 第 12 页。图 12 是远端网卡收到非批量操作的微基准。只跟踪 READ 的实测系列与 InfiniBand 理论上限；暂不看 UC WRITE。横轴是单次操作的数据量（字节），纵轴是每秒完成的操作数（Mops，百万操作/秒），注意子图纵轴刻度不同。

怎么解释： 小请求时，即使链路还有空余容量，网卡每秒能处理的请求数也有限；数据变大后，每个完成的请求带走更多字节，链路逐渐成为限制，操作数/秒下降不等于搬运字节/秒下降。作者给出的这些转折点来自各自平台，不能只归因于网卡型号，因为带宽与其他配置也不同。

不证明什么： 图中没有对照 TCP 或完整存储 RPC，也没测本课 4 KiB 读延迟、尾延迟、SSD 缺页路径或生产收益。它支持的是“瓶颈会随单次字节数与硬件改变”，而不是“READ 必然比 RPC 快”。

05 / 不需要网卡的课后题（4 分钟）

同一个 block_id：① B 上缓存命中，A 只有块号；② A 已得到有效地址和 rkey，数据还在注册缓冲区；③ B 在完成读取前淘汰缓存，并可能重新使用这段地址。分别写下：谁决定数据在哪？谁搬数据？A 看见成功完成后，能否交付给应用？

展开参考答案
  1. 只有块号，需先查元数据。可让 B 应用处理 RPC，或先查询元数据再决定怎样搬；网卡不会解释块号。
  2. 此前已决策并授权，RNIC 负责跨网搬运；成功完成说明 READ 完成。在一致性和生命周期条件都满足时才交付，而不是单凭 CQE 判断新鲜度。
  3. 地址存在且 READ 成功也可能读到被复用的内容。安全做法要保护缓冲区的有效期，例如钉住直到在途读取结束，或配合版本/有效期检查与回退。如发现过期，重新查询或走 RPC，不要静默返回。这里是工程设计提示，不是论文实验结论。

工程取舍：先从只读、已定位的热数据考虑单边搬运；若每次都要额外查询、校验或频繁回收，远端少执行一次处理的收益可能被新路径吞掉。验证时把缓存命中/未命中拆开，把查询和搬运都计入端到端延迟，并检查失效场景的正确性，再对比服务端 CPU 和 p99（99% 请求都不超过的延迟）。
