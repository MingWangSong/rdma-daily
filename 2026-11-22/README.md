## FCP：拆开 RDMA 设备打开、注册与连接建立的启动成本

ACM SoCC 2026 · 2026-11-18 至 11-20（会议；11-19 报告，近期非本日新刊） · 中国科学技术大学、香港科技大学、东南大学

区分冷、暖与 fork 启动，优化用户态 libibverbs，以 INIT 父进程预留同租户 RC 连接降低子 worker 首读之前的开销。

### 问题：弹性扩容时，RDMA 慢在打开设备还是传输？

频繁启动的客户端要重新枚举／打开设备、分配 PD、注册 MR 和建 QP。过去用内核池预建连接来解决启动，但可能把系统调用带回数据路径。FCP 拆分三个时标：新容器冷启通常由容器创建主导；现有容器 warm start 才暴露毫秒级 verbs 开销；预热进程 fork 的收益则要求把绝大部分 RDMA 初始化提前。

### 机制：优先缩短初始化，再把 QP 交给子进程

- **冷／暖启：** libfcp 对 provider 依赖的用户态开销做采样，保留依赖输入或系统状态的调用，简化或缓存经验证稳定的部分。例如老的 Sandy Bridge 探测逐核检查，在目标现代 mlx5 设备上结果不变；这不是允许在所有机器硬编码。未验证的 provider 走普通 libibverbs。INIT 可让 RDMA 建立与 Python 包导入并行，但性能主因仍是 open device 开销下降，不是并行掩盖。
- **Fork 启动：** 编排器根据已知目的端找持有连接的容器 INIT；同一用户容器内的父进程预备 context、PD、32 KB MR 和 RC QP。分配表以 QP ID 记录子 PID／目的；优先挑未分配且目的匹配的项，池 miss 才连接 RESET QP。分配表仅由 INIT 更新，避免多个孩子同时认领同一 QP；孩子退出后槽位回收。数据路径是孩子持 QP 直接走用户态，不经过本地代理转发；代价是预留 RNIC 状态、注册内存，且只能在有父子关系进程中继承。作者以 Linux 5.9.0-rc7 的 copy-on-fork 支持为兼容边界；较早版本可在 INIT 启动时使用 ibv_fork_init。据此仍须验证实际内核、rdma-core 和 RNIC/provider 组合。非 fork 的 JVM／Pod 不应视为同一路径。
- **边界：** 原型以已知目的地址及同用户容器复用为前提。不同租户、异常退出后残留 WR／CQ、远端连接重新建链、MR/rkey 的生命周期均须单独验证；不把控制面复用当成跨租户共享许可或一致性保证。32 KB 是预分配内存，不是大块吞吐实验的容量结论。

### 证据：用一样的指标比较，不把微基准当业务

- **图 6／§5.2：** 双 Intel Xeon Gold 5218R／256 GB 每台、两台 100 Gb/s ConnectX-5、SN2700、PFC/ECN；Linux 5.15 Ubuntu 22.04，KRCore 单独用 Ubuntu 18.04 / 4.15.0-46。每个 CPU 配置重复 10 次；原生 libibverbs 跨配置平均关键路径 21 ms，P90 的跨配置均值 25 ms；libfcp 分别 2.2 ms、2.3 ms（9.5×、10.7×）。对照的 P90 不是生产连接风暴总耗时，也不是端到端读 P99。
- **图 7／§5.3：** 冷启动中单容器启动约 318 ms，约占原生 verbs 总时间 93.5%、FCP 总时间 99.0%，故库优化收益相对小；暖启约 89 ms，原生 verbs 增 40.0%，FCP 暖启端到端比 KRCore 慢 2.2%。计时从请求启动到 QP 连接建立，不包含业务读。Python fork 基线 1383.86 µs，FCP 只多 90.52 µs（约 6.5%）；KRCore 1402.56 µs。池命中选现有 QP 花不到 1 µs；池 miss 时按需建 QP 的平均耗时为 258.94 µs、P90 为 306.07 µs；若把这一步留在关键路径，作者估算比 Python fork 基线慢约 25%。不要把 pool hit 当作连接新 endpoint。
- **图 11／§5.4：** 20 线程单边 READ 的 P99/P99.9，FCP 2.83/3.06 µs，KRCore RC 3.78/4.23 µs，KRCore DCT 3.85/6.79 µs。作者将 KRCore RC 的额外尾延迟归因于数据路径跨内核，而 DCT 的进一步长尾与偶发重连相符；对普通用户态 libibverbs 数据路径的结果接近，不能宣称 FCP 对标准 RDMA 快 46.5%。这些是 verbs 微基准，不是 NVMe、对象缓存或跨 AZ 服务的端到端结果。

### 存储落地：先拆“启动到首个正确读”

在反复创建短寿命预取／扫描 worker 或快速恢复 metadata client 时，先追踪 open、注册、QP connect、连接缓存命中与首个校验读，区分容器编排和 RDMA 时间。用 2–4 台主机测试原生 verbs、仅快初始化、同租户同目的预建池三条路径；扫目的节点基数、突发启动、连接失效和 MR 大小，测 p99 首读、RNIC QP 预算、注册内存占用以及故障后重试正确性。长存储进程一般先提高连接复用、核实热点是否仍是 open；不要为小收益引入新的父子进程生命周期。

## TRAM：让跨分片元数据按树排序，而不是让所有分片互相对表

ACM SoCC 2026 · 2026-11-18 至 11-20（会议；11-18 报告；近期正式发表，非今日新发） · Università della Svizzera italiana（瑞士意大利语区大学）、Politecnico di Milano（米兰理工大学）

客户端写入目的组的最近公共祖先；各组用单边 RDMA 日志写入推进组内共识，并沿树转发，降低多分片全互联协调。小消息获益，跨层延迟、负载偏斜与故障重连仍有代价。

### 问题：何时需要为跨分片元数据排序？

对同时修改多个分片的请求，仅在每个分片分别追加日志，不能保证交叉请求在共享目的分片看到相容顺序。集中排序把无交集请求也串起来；RamCast 一类方案只动用目的组，但增大目的组数时，传递逻辑时间与跨组确认会迅速增加。TRAM 以固定树换协调成本：小范围请求在局部处理，较大请求从必要的公共祖先下发；可能经过不执行该请求的中间组。

### 机制：输入缓冲、组内日志、按槽转发是三次不同的进度

- **正常路径（§4–5、图 3）：** 客户端根据已知树计算所有目的组的最近公共祖先 LCA，对 LCA 每副本的客户端专用输入缓冲 HM 发布带唯一 ID 和目的集合的消息。组长轮询输入槽，把选中的消息复制到本组 LOG，用单边 RDMA 写向被动副本并等待组内法定人数成功；自身属于目的组才交付，然后向能够到达目标的子组并行写其父组输入槽。子组重复这个过程；父子之间 FIFO 保留上游已经决定的次序。有共同目的组的消息，其两个 LCA 必是祖先／后代关系，因此下游可继续确定它们的相对次序。此机制不要求各目的组交换全局逻辑时钟；组内接管仍需要类似 Paxos ballot 的时间戳。
- **接管（§5.4–5.6）：** 新 leader 申请带时间戳的写权限，由副本撤销旧 leader 的写许可。读取组内副本的未决日志槽，选最高时间戳项并重新复制以确认，再按日志里记录的输出槽位置重写可能尚未发至子组的消息，恢复输入／输出游标。这样区分“组内已决定、子组未收到”的窗口，不把旧连接写完成当作全树交付。模型是假设 crash-stop、组内法定人数仍可用并最终稳定选主，不是拜占庭容错、整组掉电持久化或动态拓扑迁移。
- **RNIC/内存前提（§6）：** 原型用末尾 canary 检查到达，依赖目标 RNIC 上按地址方向可见和对齐缓存行原子性；标准未普遍保证这种可见性，不能换网卡就假设正确。应在新平台用显式完整性校验或有据可核的同步机制。每条消息进入 HM 后又复制到 LOG，不等于端到端无拷贝。

### 证据：吞吐获益与故障代价并存

- **图 5／§7.1、7.3：** CloudLab R320，8 核 Xeon E5-2450／16 GB，Mellanox ConnectX-3 FDR InfiniBand；标称链路 50 Gb/s，作者用 ib_write_lat 测得单边写延迟 1.31 µs。图 5 用 8 组、每组 3 副本、64 B、均匀随机目的组。八目的组时广树相对 RamCast 的单客户端延迟约缩短至 1/2.3，基础树饱和吞吐超过 3×；是不同树型、不同负载，不能合并为同一条曲线。少目的组时 RamCast 有优势；广树满载时根成为瓶颈，深树反而更适合高吞吐。
- **图 7／§7.5：** 8 目的组、每组 3 副本，TRAM 用广树测延迟、深树测吞吐。扩大消息后 HM → LOG 的本地复制成本上升，约 16 KiB 时与 RamCast 接近；不是“原子广播可以替大对象高速数据流”。图 10 中相对消息传递的 5.9×／106× 使用非复制 Java ByzCast 对照，不能隔离为纯协议或纯 RDMA 的收益。
- **表 1／§7.9：** 8 组同时换主、100 客户端均发往全部 8 组，共做 3 轮。受影响消息的端到端交付延迟均值 28.251 ms、范围 4.42–50.73 ms，不是整轮故障切换耗时，权限错误后 QP 恢复是论文指出的主要成本。不要把单边写的微秒级时延当作故障恢复时间，也不要将范围上界写成生产 P99。

### 存储落地：先在元数据提交里验证

可先试跨分片目录更新或小对象元数据排序，不替换已有数据复制、持久化和恢复协议。用 3 组各 3 副本的实验集群，重放真实元数据目的组分布，与现有组内共识＋跨组协调对照：调 1–3 组扇出、64 B–16 KiB、热门路径偏斜和客户端并发；分别记录交付延迟 P50/P99、满载消息率、根与中间组 CPU、QP 数和 pinned memory。让组长分别在组内写完成后、子组转发前退出，检查按槽恢复后无漏发／重复执行，统计 QP 恢复到重新服务的实际间隔；将应用幂等提交和持久化验收与协议交付分开。此为工程验证建议，不是论文已经证明的文件系统结果。
