副本保证可靠性，缓存不必复制三遍

LDC 精读：通过单边 RDMA 共享副本内嵌缓存，把冷写污染、热点复制与一致性验证放回同一条数据路径。

冗余不只来自读请求落到不同副本

传统副本内缓存彼此独立。按 key 路由读请求能减少读造成的重复缓存，却挡不住复制写：每个副本应用同一个更新，都会把对象带入自己的缓存。更复杂的嵌套查询和 join 在执行前不知道最终访问哪些 key，客户端也无法提前正确路由。LDC 不新建一套独立缓存集群，而是把现有存储副本的内嵌缓存逻辑合并：介质上的持久副本数不变，内存驻留可以不同。这是容量利用优化，不是降低数据容错副本数。

读、写、热点复制的实际路径（§3–4）

  1. 本地命中优先，远端只作缓存层。 各副本保留本地缓存索引，并懒传播索引更新。读 miss 后用本地保存的远端索引定位对象，一次单边 RDMA READ 读取远端缓存，不让对端 CPU 服务该读；仍需本机 CPU 做查询、验证、统计和管理。远端命中默认不再准入本地缓存，只有所有缓存都没找到才读取本机磁盘并准入。
  2. 索引是 hint，不是正确性证明。 远端地址可能已被淘汰复用，因此对象中携带 ID，读到错误 ID 就回退本地磁盘。与写入并发时，用对象 checksum 检查撕裂，失败则重读。论文 Zipf 测试中约 0.5% 远端访问遇到陈旧索引，不能将其当成任意工作负载的上界。checksum 检查完整性，不自动提供线性一致性。
  3. 写 miss 进入 tiny queue，而不是污染主缓存。 如果副本已缓存该对象，直接原地更新主缓存；否则写入从总缓存预算中切出的 tiny queue，周期性写盘并淘汰。实验队列大小为缓存的 0.01%，不是额外免费内存。该队列不暴露给其他副本；读取队列对象时，先看别处是否已有主缓存副本，再决定提升到本机主缓存。这样保留写合并/异步刷盘，又限制冷写污染范围。队列太小可能使写等待刷盘，不应承诺写延迟必降。
  4. 热对象允许冗余，但有成本模型。 CBA 每隔 t 秒统计窗口访问频率并排序，扫描在 N 个副本都缓存前 R 个热点的成本。R 个对象占用 N×R 份容量，使唯一覆盖对象数减少 (N−1)R；模型比较节省的远端 RDMA 延迟与被挤出对象新增的磁盘延迟。local/RDMA/disk 延迟取上个窗口实测值，不是写死常数。各副本独立选择 Ropt，远端命中落在热点集合才准入；降低目标后停止新准入，依靠淘汰逐渐收敛。这依赖频率可预测、延迟测量有代表性，不能保证突变 workload 下瞬时最优。

图4（PDF第6页）用 F 的写入揭示选择性：R3 原本有 F，留在主缓存；R1/R2 没有 F，写入私有小队列。这不是无差别把全部写绕过缓存，否则就会将同步磁盘开销重新放回写关键路径。

一致性和失效：保留上层协议，不用 RDMA 替代协议

Twig-kv 使用异步 primary-backup，读可在任意副本，提供最终一致性；其快速写返回不能解释为所有副本已持久化。Craq-kv 则沿链传播 dirty version，尾副本提交后反向更新 clean version；clean=dirty 才能直接读，否则查询尾副本。LDC 远端读取必须把 clean/dirty 版本一起取回，仍交上层执行同样的版本判断。仅校验 ID/checksum 不足以跳过这些步骤。

副本失效导致 RDMA 失败时回退磁盘，CBA 按剩余容量重算。论文据此主张不增加单点故障，但没有单独给出故障注入、RDMA timeout 或恢复 p99 实验。实际系统仍要验证超时之前的尾延迟、重试风暴、缓存地址复用，以及刷盘队列与原有日志/复制提交点的契约。RethinkDB 集成只实现读路径，没有实现写路径，不能把三种系统都称作完整读写生产验证。

实验：避免拿 SATA 峰值当现代 NVMe 的默认收益

主实验为 3 个副本（部分扩至5个），每机 Xeon E5-2640v4 10核、64GB DRAM、25Gb ConnectX-4、480GB SATA SSD；默认1000万条、24B key/100B value，客户端读保持 sticky session，写到 leader。每副本缓存比例相对于完整数据集，33.3%×3代表总预算约能容纳一份数据集。主分析对照 OrigCache、禁用小队列的 LDC-no-tq；其他对照包括 key routing、n-chance cooperative caching、S3-FIFO。

图8（PDF第10页）固定每副本33.3%缓存、Zipf访问，扫描1%/5%/50%写。50%写时，完整 LDC 相比 OrigCache 吞吐4.2×、相比 no-tq 1.5×；只优化远端读却不处理写污染，覆盖率随写比例上升而下降。图8(d)是在50%写下的读写延迟：小队列使写相对原版增加约10μs，但读降低5.8×。这是延迟柱状结果，未给出 p99，不能描述成尾延迟下降5.8×。

图11（PDF第11页）换用 NVMe SSD 后，YCSB C/A 吞吐分别为原版2.2×/2.5×，小于部分 SATA 实验的最高倍数，但依然显示减少重复缓存不只对慢盘有效。该节未明确 NVMe 型号，不补写型号、QD或持久化能力。RethinkDB 只读测试为最高1.9×；其远端索引每远端副本每4KB页8B，含CBA统计的额外内存低于1%，这是该页粒度实现的结果，不可直接外推到100B对象或数十副本。

50条真实 trace 的平均延迟结果来自模拟器：模拟命中类别后代入实机延迟，并非50种生产部署实测。Twitter 47条的平均改善1.57×、最大5.76×；Meta/Alibaba 分别1.46×/1.39×。模型主要优化平均代价，若目标是 p99/SLO，需要另加超时、热点带宽与队列限制。3→5副本实验依然是小规模验证，并没有验证百节点全量索引交换成本。

分布式存储落地建议（以下为本报告推断）

最适合先试已有多副本、读可在多个副本执行、内嵌 block/page cache 重复率高的存储引擎，而不是已经按 key 严格分片且不缓存写入的外部缓存。先从 trace 计算跨副本唯一覆盖率，区分复制写污染和热点有益副本；如果 miss 主因是容量不足且远端内存远快于盘，LDC 才有明确空间。

最小原型采用3副本同总内存，比较本地缓存、仅远端read、不准入冷写、带CBA四组；扫描缓存比例、1/5/50%写、均匀/Zipf/热点迁移，分别跑 SATA 与实际 NVMe。监控唯一覆盖率、远端hit、索引失效率、checksum重试、每请求RDMA字节、RNIC/PCIe/CPU占用、tiny queue阻塞和刷盘量，同时测p50/p99/p999。热点对象多次远端读取可能让RNIC成为瓶颈，不能只看缓存命中率。

上线前专门做陈旧索引复用、远端读取中途修改、主缓存淘汰、tiny queue满、网络分区和副本重启。对于强一致缓存，版本/epoch应跟业务对象一起验证，重试有界并回退原读路径。原论文 checksum 机制还需按实际 CPU/RNIC 写入顺序核对，不能当作任意大小 RDMA READ 原子保证。
